flutter_reap · module topology

How the reaper works

Five collectors answer one question each. The plan assembles their answers and hands back a list — it never deletes and never prints. Nothing is removed until a human answers a prompt.

Runtime

What happens on every run

Three gates stand between typing the command and losing a directory. Two of them are passed by doing nothing at all.

THE THREE EXITS

Every path that doesn't delete is reached by inaction. No candidates found and it stops. No --delete flag and it stops. An unparseable answer, a k, or a closed stdin and it stops. Deletion is the only outcome that requires you to have typed something deliberate at a prompt that has just listed every path.

Even past that gate, deleter re-checks every path itself rather than trusting the plan: a directory is removed only if its final segment is a known generated name — and never if it sits directly under a filesystem root.

Using it

Install once, run anywhere

STEP ONE

Install globally

dart pub global activate flutter_reap

Puts a flutter_reap executable in ~/.pub-cache/bin — on Windows, %LOCALAPPDATA%\Pub\Cache\bin. If that isn't on your PATH yet:

export PATH="$PATH:$HOME/.pub-cache/bin"

Anyone with Flutter already has the Dart toolchain, so there is nothing else to install.

STEP TWO

Look, delete nothing

flutter_reap ~
flutter_reap ~ --days 90
flutter_reap ~ --no-caches
flutter_reap ~ --json
  • --days 90 — only projects untouched for 90+ days
  • --no-caches — projects only, skip DerivedData and Gradle
  • --json — machine-readable, always a dry run
  • --help, --version

STEP THREE

Delete, with a gate

flutter_reap ~ --delete

Prints the numbered list, then asks:

keep which? (e.g. 1,3-5)
  [enter] delete everything listed
  [k]     keep everything, cancel

Anything unparseable cancels. For CI, --yes skips the prompt — and is rejected unless combined with --days:

flutter_reap ~ --days 90 --delete --yes

READING A ROW

  1.   1840M   214d !  ~/AndroidStudioProjects/old-client-app
       └ size  └ idle └ uncommitted changes

Idle comes from the last commit, never the build directory's timestamp — that resets on every build, so a long-dead project would look freshly touched. The ! marks a project with uncommitted work: deleting its build/ is still safe, but it means someone is mid-flight there.

The ~ matters. Machine-wide caches and unused fvm SDKs are only ever offered when the scan root is your actual home directory. Point it at a subfolder and it stays scoped to projects under that folder — narrowing the root can never widen what is at risk.
